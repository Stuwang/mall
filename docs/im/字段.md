# 关键字段

会话没有单独的表。一场私聊的 `conv_id` 是 `{较小用户id}_{较大用户id}`，按整数比较大小，再拼成字符串。`12_3` 和 `1_23` 是两场不同的会话。两边的成员行和消息行都写这个 id。

下面用 A、B 表示两个用户，并且假设 `A < B`，所以 A 的同步序号存在 `seq_low`，B 的存在 `seq_high`。A 比 B 大时，两列对调，规则不变。

## 消息 id

`im_message.id`，全局自增，一条消息一个。

它用来：

- 唯一指向这一行，客户端用它覆盖本地消息
- 成员行上的 `last_msg_id` 指向「这个用户列表上的最新一条」
- 和 `ct` 一起决定气泡先后

它不用来：

- 做增量同步的游标
- 判断两个用户谁看到了更多消息

创建之后 `msg_id` 和 `ct` 都不再改。正文更新不会把这条气泡挪到时间线末尾。

## 同步序号和 last_seq

每个用户一条计数，跨他的全部会话递增。一场会话里的 `last_seq` 只表示「这些号里面，落在这一场、并且这个用户看得到的最大那个」。

| 字段 | 在哪 | 含义 |
|------|------|------|
| `im_user_seq.seq` | 用户计数 | 这个用户已经分配过的最大同步序号 |
| `seq_low` / `seq_high` | 消息 | 这一侧当前的同步序号。看不见为 0。更新后改成更大的新值，旧值留空 |
| `last_seq` | 成员行 | 这一侧在这场会话里的最大同步序号 |

同一条双方都可见的消息，A 的序号和 B 的序号各自取，不必相等。比较两个人的 `last_seq` 没有意义。

列表增量比较的是**同一个用户**名下各会话的 `last_seq`。所以序号必须在这个用户的所有会话之间单调递增。某一场若自己从 1 另起一套号，列表游标会对不齐。

下行消息里的 `seq` 是当前用户的那一列。

更大的序号已经能被读到时，更小的序号已经在同一次取号事务里提交过了。中间可以缺号：更新把旧号作废，或者这个号发给了另一场会话。缺号不表示删除。

## 最新消息和排序时间

这些列是会话列表上的预览，按创建顺序挑选，不按同步序号挑选：

| 列 | 含义 |
|----|------|
| `last_msg_id` | 这一侧当前最新消息的 id。没有则 0 |
| `last_sender_id` | 那条消息的名义发送者 |
| `last_preview` | 文本摘要 |
| `sort_ut` | 那条消息的 `ut`。展示按它倒序，相同则 `last_msg_id` 倒序 |

「更新」指这条消息的创建比该侧当前最新一条更晚（`ct` 更大，相同则 `msg_id` 更大）。同步序号变大不会让一条旧消息变成最新。

因此：

- 新消息，且这一侧预览开关为真：它成为最新消息，`sort_ut` 用它的 `ut`
- 新消息，预览开关为假：历史里有它，`last_seq` 增加，最新消息和 `sort_ut` 不动
- 更新一条旧消息：`last_seq` 增加，最新消息和 `sort_ut` 不动
- 更新的就是当前最新那条，且预览开关为真：摘要改成新正文，`sort_ut` 改成新的 `ut`，会话会浮上去

内部发送的两个开关只在上述规则里生效，不能把一条更早的消息改成最新：

| 字段 | 为真时 |
|------|--------|
| `sender_preview` | 名义发送者按上面的规则更新预览 |
| `peer_preview` | 对端按同样规则更新预览 |

两个开关互不影响。用户自己发送时，两个开关都为真。

某一侧不可见，却把该侧预览开关打开：拒绝。看不见的一侧不取号，也不建成员行。

## 谁发出的，谁能看见

| 字段 | 取值 |
|------|------|
| `sender_id` | 名义发送者。系统代替 A 发时，这里仍是 A |
| `origin` | 1 用户自己发，2 系统代发 |
| `visibility` | 1 仅对方可见，2 仅发送者可见，3 双方可见 |

用户自己发：`origin = 1`，`visibility` 固定为 3。客户端不能改可见性。

系统代发的三种情况，名义发送者都是 A，对端都是 B：

| visibility | 谁取同步序号 | A 的序号 | B 的序号 |
|------------|----------------|----------|----------|
| 1 仅对方 | 只动 B 的计数 | 0 | B 的新序号 |
| 2 仅发送者 | 只动 A 的计数 | A 的新序号 | 0 |
| 3 双方 | A 和 B 的计数都加 | A 的新序号 | B 的新序号 |

下行给用户的消息带 `origin` 和 `sender_id`，不带 `visibility`。

## 幂等键

`idempotency_key` 加 `origin`、`sender_id` 唯一。

| 来源 | 键从哪来 |
|------|----------|
| 用户发送 | 客户端生成的 `client_msg_id`，8 到 64 位，`[A-Za-z0-9_-]` |
| 系统代发 | 调用方生成的 `request_id`，规则相同 |

空键拒绝。命中旧键且 `content_type`、正文与第一次相同：返回原消息，不取新序号。命中旧键但正文不同：拒绝，不插入第二条，也不改已有行。用户改了字再发，要换一个新的 `client_msg_id`。

## 不变量

1. 一个用户的同步序号来自他那一行计数，跨会话递增。只有他看得到的新建和更新才取号。
2. 某场会话的 `last_seq` 等于这个用户在这场里当前最大的同步序号。取号、写消息、改 `last_seq` 在同一个事务里。
3. 序号可以缺。缺号是作废的旧号，或发给了这个用户的其他会话。缺号不代表有一条还没同步的消息。
4. 更大的序号对同步接口可见时，更小的序号已经提交。
5. 序号 0 只表示「这一侧不可见」，不占用该用户的计数。
6. 不可见的一侧不改 `last_seq` 和预览，也不为此新建成员行。
7. `last_msg_id` 按创建顺序维护。同步序号和 `ut` 不能把一条更早的消息提升为最新。
8. 会话内气泡先后以 `ct`、`msg_id` 为准。同步序号只负责把新建和后来的更新拉下来。

## 例子

A、B 的计数一开始都是 0，都没有成员行。下面每格写的是该用户自己的同步序号。预览开关除特别说明外都为真。

**1. A 自己发「你好」，双方可见**

A 的计数变为 1，B 的计数变为 1。双方都建成员行，最新消息都是 id=1。

| | 消息 id | A 的序号 | B 的序号 | A.last_seq | B.last_seq | 双方最新 |
|--|---------|----------|----------|------------|------------|----------|
| 结果 | 1 | 1 | 1 | 1 | 1 | id=1 |

**2. 系统代替 A 发给 B，只有 B 可见**

只给 B 取号。A 的计数、`last_seq`、最新消息都不动。

| | 消息 id | A 的序号 | B 的序号 | A.last_seq | B.last_seq | A 最新 | B 最新 |
|--|---------|----------|----------|------------|------------|--------|--------|
| 结果 | 2 | 0 | 2 | 仍是 1 | 2 | 仍是 id=1 | id=2 |

A 的历史里不会出现 id=2。B 下次用 `after_seq = 1` 能拉到它。

**3. 更新 id=1 的正文**

双方都还看得见 id=1，所以两边都再取一个号。id=1 在 A 侧从 1 改成 2，在 B 侧从 1 改成 3。旧的 1 留空。

A 的最新仍是 id=1，所以 A 的摘要和 `sort_ut` 跟着新正文变。B 的最新已经是 id=2，B 的摘要和 `sort_ut` 不变，只有 `last_seq` 变成 3。B 的历史用 `after_seq = 2` 会再次拿到 id=1，客户端按消息 id 盖掉本地那条。

| | A 的序号 | B 的序号 | A.last_seq | B.last_seq | A 最新 | B 最新 |
|--|----------|----------|------------|------------|--------|--------|
| id=1 更新后 | 2 | 3 | 2 | 3 | id=1 | 仍是 id=2 |
| id=2 未改 | 0 | 2 | | | | |

**4. 系统消息只有 A 可见，并且 A 的预览开关为假**

A 再取号，消息 id=3，A 的序号为 3。`last_seq` 变成 3，所以列表同步会带回这场会话。最新消息仍是 id=1，摘要不变。A 打开会话时，历史接口把 id=3 补进本地。
