# 库表

库文件是 IM 进程自己的 `im.db`。时间是 unix 秒，字段名 `ct` / `ut`。

消息不删除。本期没有撤回、拉黑、隐藏。

`user`、`user_login` 由 user 模块建在同一个库里，结构以该模块为准。

聊天只有两张表。不建 `im_conversation`，不建回执表、设备表、拉黑表。

字段怎么一起变化，见 [字段](字段.md)。

## im_conversation_member

每个用户在一场私聊里一行。原来会话表上的字段放在这里，值按这一侧单独维护。

| 列 | 类型 | 说明 |
|----|------|------|
| id | int64 PK | 自增。只标识这一行，不作为两边共用的会话 id |
| user_id | int64 | 这一行属于谁 |
| peer_user_id | int64 | 对方 |
| user_low | int64 | `min(user_id, peer_user_id)`，与消息表对齐 |
| user_high | int64 | `max(user_id, peer_user_id)`。约束 `user_low < user_high` |
| last_seq | int64 | 这个用户已经分配到的最大视图序号。没有消息时为 0 |
| last_sync_seq | int64 | 本场已经分配过的最大同步序号。两边都有成员行时，两行的值相同 |
| last_msg_id | int64 | 这个用户预览所指向的消息 id。没有时为 0 |
| last_sender_id | int64 | 那条消息的名义发送者。没有时为 0 |
| last_preview | string | 那条文本的摘要，最多约 50 个码位 |
| last_msg_at | int64 | 那条消息的 `ct`。列表排序用。没有时为 0 |
| ct / ut | int64 | |

唯一索引：`(user_id, peer_user_id)`。

列表：`user_id = ?`，按 `last_msg_at` 倒序。索引 `(user_id, last_msg_at)`。

双方两行的 `user_low`、`user_high` 相同。`last_seq` 和 `last_msg_*` 可以不同。

## im_message

| 列 | 类型 | 说明 |
|----|------|------|
| id | int64 PK | 消息 id，全局自增。同步不用它当游标 |
| user_low | int64 | 这场私聊 |
| user_high | int64 | |
| sender_id | int64 | 名义发送者。系统代发时也是被代替的那个用户 |
| origin | int32 | 1 用户自己发，2 系统代发 |
| visibility | int32 | 1 仅对方可见，2 仅发送者可见，3 双方可见。用户自己发恒为 3 |
| seq | int64 | 同步序号。新建时分配；这条消息以后被更新时，改成当时更大的新序号 |
| seq_low | int64 | `user_low` 的视图序号。创建时写入，之后不改。他看不见则为 0 |
| seq_high | int64 | `user_high` 的视图序号。创建时写入，之后不改。他看不见则为 0 |
| idempotency_key | string | 用户发送是 `client_msg_id`，系统代发是 `request_id` |
| content_type | int32 | 1 文本。其他正整数保留，一期拒绝写入 |
| content | text | JSON。一期只有 `{"text":"..."}` |
| ct / ut | int64 | 创建写 `ct`。更新正文或同步序号时改 `ut` |

唯一索引：

- `(origin, sender_id, idempotency_key)`
- `(user_low, user_high, seq)`
- `(user_low, user_high, seq_low)`，仅 `seq_low > 0`
- `(user_low, user_high, seq_high)`，仅 `seq_high > 0`

后两个用部分唯一索引，这样多条「某一侧不可见」的消息都可以把该侧序号存成 0。

某个用户拉自己的历史时：自己是 `user_low` 就用 `seq_low`，否则用 `seq_high`。条件是序号大于游标且序号大于 0，按该序号升序。

## 一次写入动哪些行

新建一条消息：

1. 可见的一侧保证成员行存在。不可见且还没有成员行的一侧不建。
2. 同步序号取该私聊 `max(seq) + 1`，写入消息的 `seq`。已经存在的成员行把 `last_sync_seq` 改成这个值。
3. 可见侧在同一事务里把 `last_seq` 加一，写入 `seq_low` 或 `seq_high`。不可见侧的视图序号写 0，并且不改他的 `last_seq`。
4. 某一侧的预览开关为真时，才更新该侧的 `last_msg_id`、`last_sender_id`、`last_preview`、`last_msg_at`。用户发送两侧都为真。

更新一条已有消息：

1. 改正文，`ut` 改为现在。
2. `seq` 改成该私聊新的 `max(seq) + 1`。`seq_low`、`seq_high` 不动。
3. 已有成员行的 `last_sync_seq` 改成新的 `seq`。
4. 预览开关为真的一侧，用更新后的正文重写预览字段。开关为假则预览保持原样。

幂等命中旧的新建请求时，上面的更新都不做。

锁顺序：一个事务里如果要改两行成员，按 `user_id` 从小到大加锁，避免以后换到 MySQL 时死锁。
