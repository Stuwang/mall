# 接口

聊天接口由 IM 进程提供：`POST`、JSON、响应 `{code, msg, data}`，包装用 `modules/kit` 的 httpx。用户接口前缀 `/im/api/v1/`。用户 id 从鉴权取。

注册、登录、资料、封禁挂 user 模块已有的 HTTP，不在这里列。

非 test 环境用户接口带 `Authorization: Bearer <jwt>`，密钥是 IM 自己的。test 环境带 Header `UserId`。WebSocket 的凭据见下文。

成功时 `code = 0`。业务失败同样 HTTP 200，靠 `code` 区分。

同步怎么用这些接口，见 [同步](同步.md)。序号的含义见 [字段](字段.md)。

## 用户 HTTP

自己的用户 id 不传。`BaseParam` 若为了和 user 模块的 proto 生成链对齐可以留着，服务端不从里面取身份。

请求用 `peer_user_id` 指定对端。`conv_id` 由服务端按 [字段](字段.md) 计算，出现在响应里。

### 在线用户

`POST /im/api/v1/user/online`

```json
{}
```

返回当前 WebSocket 在线的用户（不含自己），用于发起聊天。无好友关系。

```json
{
  "list": [
    { "user_id": 2, "nickname": "小王", "conn_count": 1 }
  ]
}
```

### 会话

`POST /im/api/v1/conv/list`

```json
{ "after_seq": 0, "limit": 0 }
```

`after_seq` 是这台设备已经应用过的列表游标。返回这个用户成员行里 `last_seq` 更大的会话，按 `last_seq` 升序。`limit = 0` 表示本次全部返回。正数时最多返回这么多条。

```json
{
  "list": [],
  "has_more": false
}
```

`has_more` 为真时，本批是升序前缀，下一请求的 `after_seq` 用本批最后一条的 `last_seq`。没有成员行的对端不会出现。本地还没发送成功的会话也不会出现，由客户端自己留着。

列表元素是下方的会话对象。展示时客户端再按 `sort_ut` 倒序。

### 消息

`POST /im/api/v1/msg/history`

```json
{
  "peer_user_id": 2,
  "after_seq": 0,
  "limit": 50
}
```

| 字段 | 说明 |
|------|------|
| after_seq | 这场已确认的历史游标。返回这一侧 `seq` 更大的消息，按 seq 升序 |
| limit | 0 时默认 50，最大 100 |

```json
{ "list": [], "last_seq": 0, "has_more": false }
```

`last_seq` 是这个用户成员行上的当前值。还没有成员行时，列表为空，`last_seq = 0`，`has_more = false`。对端用户不存在仍是用户不存在，对端是自己返回 1105。

`has_more` 为真表示本页已满，后面还有更大的序号。客户端把游标停在本页最后一条的 `seq` 再请求。本页没满时，游标可以拨到响应里的 `last_seq`。

`POST /im/api/v1/msg/send`

```json
{
  "peer_user_id": 2,
  "client_msg_id": "c-8f3a",
  "content_type": 1,
  "text": "你好"
}
```

双方都可见，两侧预览都更新。`content_type` 一期只能是 1。`client_msg_id` 为 8 到 64 位，字符集 `[A-Za-z0-9_-]`。

同一发送者的同一个 `client_msg_id`：

| 情况 | 结果 |
|------|------|
| 第一次 | 落库，`code = 0` |
| 再次请求，正文和 `content_type` 与第一次相同 | 返回原消息和原会话快照，不取新序号，`code = 0` |
| 再次请求，正文或 `content_type` 不同 | `code = 1108`，不改已有行，不插入第二条 |

正文按提交原文比较。用户改了字再发，使用新的 `client_msg_id`。

成员行不存在时，发送会先把双方建出来，再写入。`conv_id` 在响应的消息和会话里返回，规则是较小用户 id、下划线、较大用户 id。

```json
{
  "msg": {},
  "conv": {}
}
```

`msg.seq` 和 `conv.last_seq` 都是发送者自己的。客户端用它们显示这一条、盖住列表预览。历史游标仍等 `msg/history` 的结果再前进。

## 内部代发

`POST /im/internal/v1/msg/send`

不接受用户 JWT。Header `X-Im-System-Token` 与配置 `im.system_token` 一致。用户长连接里没有这条命令。

```json
{
  "sender_id": 1,
  "peer_user_id": 2,
  "visibility": 1,
  "sender_preview": false,
  "peer_preview": true,
  "request_id": "sys-1001",
  "content_type": 1,
  "text": "只给对方看的文本"
}
```

| 字段 | 含义 |
|------|------|
| visibility = 1 | 仅 `peer_user_id` 可见 |
| visibility = 2 | 仅 `sender_id` 可见 |
| visibility = 3 | 双方可见 |
| sender_preview | 为真时，按 [字段](字段.md) 更新名义发送者的最新消息 |
| peer_preview | 为真时，按同样规则更新对端的最新消息 |

不可见的一侧不能把对应预览开关设为 true。

`POST /im/internal/v1/msg/update` 更新已有消息的正文。看得到这条的每一侧把同步序号改成新值。`msg_id` 和 `ct` 不变。预览开关为真时，只有这条已经是该侧最新消息，才重写预览和 `sort_ut`。

`sender_id` 与 `peer_user_id` 都不能缺，且不能相同，都必须是本服务用户。`request_id` 的幂等规则与 `client_msg_id` 相同：同键同正文返回第一次的结果，同键不同正文返回 1108。

```json
{
  "msg_id": 2,
  "conv_id": "1_2",
  "sender_seq": 0,
  "peer_seq": 2
}
```

看不见的一侧序号为 0。用户接口只返回当前用户自己的 `seq`。

消息不存在返回 1104。

## 对象

会话，是当前用户自己的成员行：

```json
{
  "conv_id": "1_2",
  "peer": { "user_id": 2, "nickname": "小王" },
  "last_seq": 2,
  "last_msg_id": 3,
  "sort_ut": 1761321600,
  "last_msg": {
    "msg_id": 3,
    "sender_id": 1,
    "origin": 2,
    "content_type": 1,
    "preview": "只在我这边的文本",
    "ct": 1761321600,
    "ut": 1761321600
  }
}
```

还没有写入过预览时，`last_msg_id = 0`，`sort_ut = 0`，`last_msg` 为空对象。`last_seq` 仍可能大于 0：消息已经进了历史，只是这次没有把它设成最新。

消息：

```json
{
  "msg_id": 3,
  "conv_id": "1_2",
  "seq": 4,
  "sender_id": 1,
  "origin": 2,
  "client_msg_id": "",
  "content_type": 1,
  "content": { "text": "只在我这边的文本" },
  "ct": 1761321600,
  "ut": 1761321600
}
```

`seq` 是当前用户这一侧的同步序号。消息被更新后，这个字段变成更大的新值，`msg_id` 不变。`origin` 为 1 时是用户所发，为 2 时是系统代发。用户所发的消息带上发送者的 `client_msg_id`。系统消息这一字段为空，内部的 `request_id` 不返回给用户。

`content_type` 以外的取值一期不会出现在响应里。

## WebSocket

`GET /im/ws?access_token=<jwt>`

test 环境：`GET /im/ws?user_id=1`

帧是文本 JSON，上限 64KB。

客户端发给服务端：

```json
{ "cmd": "ping", "req_id": "1", "data": {} }
```

服务端应答：

```json
{ "cmd": "pong", "req_id": "1", "data": {} }
```

服务端主动推送没有 `req_id`：

```json
{ "cmd": "msg.push", "data": {} }
```

`data` 是消息对象，`seq` 是这条连接上的用户自己的。只推他看得到的新建和更新。发送者的其他在线连接也会收到。

长连接上没有发送，也没有发送应答，没有单独的会话更新帧，没有离线信箱。

心跳：客户端每 25 秒发 `ping`。70 秒没有入站帧，服务端关闭连接。这两个数来自服务端配置 `im.heartbeat_sec`、`im.idle_sec`。

## 错误码

通用码用 `modules/kit` 的 codeerror：参数 1000、未登录 1005、用户不存在 1007、无权限 1009、封禁 1014、系统 1。

| code | 何时 |
|------|------|
| 1104 | 内部更新的消息不存在 |
| 1105 | 对端是自己 |
| 1106 | 内部 token 不对 |
| 1107 | 文本为空或超长；`content_type` 不是 1；`client_msg_id` 或 `request_id` 不合法；`visibility` 不是 1、2、3；不可见的一侧却要求更新预览 |
| 1108 | 同一个幂等键被拿来提交了不同正文 |

用户 `send` 在对方用户存在时会把成员行补齐。历史拉一个还没有成员行的对端，返回空列表，不返回 1104。
