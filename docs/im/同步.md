# 客户端同步

客户端要保证：自己看得到的消息，按自己的视图序号一条不漏，并且只按序号排序。网络上可以后发先到，库里不会给同一个用户先提交较大的序号、再提交较小的序号。见 [字段](字段.md) 的不变量。

已读、未读不参与同步。没有「读到哪」的游标，只有「连续收到哪」。

## 本地要记住的状态

每个对端一份，建议落在本地：

| 状态 | 含义 |
|------|------|
| `confirmed_seq` | 这个序号及以前、且大于 `floor` 的消息都已拿到。新消息只会出现在它后面。0 表示还没有确认过任何一条 |
| `pending` | 已经拿到、但序号大于 `confirmed_seq + 1` 的消息，按序号暂存 |
| `floor` | 展示下界。`floor` 以前的序号还没拉，不算漏同步。从序号 1 开始同步时，`floor = 0` |
| `sending` | 自己发出、还没拿到序号的消息，按 `client_msg_id` 暂存 |

重连之后继续用本地的 `confirmed_seq`，从它后面补，不必从头拉。

服务端列表和历史都会带上这个用户当前的 `last_seq`。客户端要追上的是它。

## 唯一的推进规则

收到一条带 `seq` 的消息时（推送、拉取、发送 ack 都走这里）：

| 条件 | 动作 |
|------|------|
| `seq <= confirmed_seq` | 已有。按序号或消息 id 丢掉重复的一份 |
| `seq == confirmed_seq + 1` | 写入本地，`confirmed_seq` 加 1。然后把 `pending` 里紧挨着的下一条也按同样规则吃掉 |
| `seq > confirmed_seq + 1` | 放进 `pending`。立刻按 `after_seq = confirmed_seq` 向前拉。**不准**把 `confirmed_seq` 改成这条的序号 |

展示只渲染 `1 .. confirmed_seq` 里、且 `seq > floor` 的消息，再在末尾画还没有序号的 `sending`。`pending` 里的消息先不插进时间线，避免用户看到跳号，也避免界面先画了 6、却再也不去要 5。

排序只认 `seq`。`ct` 相同或更晚，都不能插到更小的序号前面。

## 拉取

`msg/history`，`direction = 2`（向更新）：

```json
{ "peer_user_id": 2, "after_seq": 10, "limit": 50 }
```

服务端返回该用户视图里 `seq > after_seq` 的消息，**按 seq 升序**，并带上此刻的 `last_seq`。`has_more` 表示这次返回的最大序号仍小于 `last_seq`。

客户端处理这一页：

1. 若列表为空：再看响应里的 `last_seq`。等于 `confirmed_seq` 则已经追上；大于则过一会重试。按不变量，提交后的序号都能读到，空页又落后于 `last_seq` 只应是瞬时失败。
2. 若第一条的 `seq > confirmed_seq + 1`：整页放进 `pending`，重试。不要把游标拨到第一条前面，那会把洞标成已确认。
3. 否则从第一条开始按推进规则吃。页中间一旦断号，断号之后的放进 `pending`，然后重试。

向更早翻页是 `direction = 1`，只移动 `floor` 和展示缓存，不修改 `confirmed_seq`，也不把旧页当成补洞的依据。

## 推送

`msg.push` 和发送 ack 里的消息，与拉取用同一个函数处理。

同一条连接上服务端会尽量按序号推。下面这些情况仍然会乱序，所以客户端不能假设下一条推送就是 `confirmed_seq + 1`：

- 发送 ack 走请求的响应，推送走另一条通道，谁先到不确定
- 一个用户有多条连接，每条连接单独收
- 进程内部若用多个任务发帧，后提交的任务可能先写完连接

## 并发场景

### 后发的消息先到

A 连续发了两条，序号将是 5 和 6。6 的推送先到。

正确：

1. `confirmed_seq` 仍是 4，6 进入 `pending`
2. 拉取 `after_seq = 4`，得到 5、6
3. 先确认 5，再从 `pending` 取出 6
4. `confirmed_seq` 变成 6

若把游标直接改成 6，再拉 `after_seq = 6`，5 就永远不在结果里。这就是漏消息。

### 推送和拉取交叠

拉取已经在途，期间推送先到了 5。拉取结果里又有 5 和 6。

5 会进来两次。第一次把 `confirmed_seq` 推到 5，第二次因为 `seq <= confirmed_seq` 丢掉。6 只确认一次。本地按消息 id 再挡一层重复即可。

### 先读到 last_seq，后写入新消息

客户端看到 `last_seq = 10`，准备拉取。在响应生成前又提交了 11。

升序拉取会带回 11，或者这一页的 `has_more` 为真、响应里的 `last_seq` 已经是 11。循环拉到 `confirmed_seq == last_seq` 为止。不要缓存页面上旧的 `last_seq` 当作终点。

### 库不会先交出较大序号

同一用户的 5 还在事务里时，6 拿不到成员行上的锁，不能提交。所以不存在「拉取只返回 6、5 尚未提交」这种洞。客户端见到的洞来自投递顺序，重试拉取就能补上。若某次拉取的第一条已经跳号，按上一节重试，仍然不要改写 `confirmed_seq`。

### 发送 ack 和推送都到了

本地 `sending` 里有 `client_msg_id`。ack 或推送谁先到，都用这个键对上同一条，写上 `seq`，再进推进规则。对不上序号之前，它一直留在时间线末尾的发送区，不占用 `confirmed_seq`。

ack 丢了：后面的拉取和推送仍带着同一个 `client_msg_id` 和 `seq`。用同一个键重试发送，服务端返回原消息，不会再发一条。

### 多端

每台设备保存自己的 `confirmed_seq`。一台已经确认到 10，另一台还停在 7，互不影响。服务端两个连接都会收到推送。一台先收到 9、后收到 8 时，仍用缓冲，不把 8 当成过期消息丢掉。

### 只有一侧看得见

系统写了一条只有 B 看得见的消息。B 的 `last_seq` 加 1，推送给 B。A 的 `last_seq` 不变，A 的连接上没有这条推送，A 的拉取也不会返回它。A 的序号仍然连续，不需要为这条「缺失的 id」补洞。

只有 A 看得见时，对调即可。

### 第一次对齐

逐条推进的规则从「已经有一个可信的 `confirmed_seq`」之后才使用。第一次对齐可以只拿最近一页，这一次允许直接落下一段连续区间。

`last_seq = 100` 时，向更早拉一页，例如得到 81 到 100。检查：

- 这一段自身连续
- 最大序号等于这次对齐中读到的 `last_seq`

然后同时写下：`floor = 80`，`confirmed_seq = 100`。1 到 80 不在本地，留给向上翻页，不算漏同步。此步骤之后，只允许按 `confirmed_seq + 1` 向前推进，不准再跳。

若这段的最大序号已经小于最新的 `last_seq`（对齐期间又写入了 101、102）：不要把 `confirmed_seq` 停在 100。从这段最大序号用 `direction = 2` 继续拉，接到最新的 `last_seq` 且中间连续，再一起写下 `floor` 和 `confirmed_seq`。这段时间里先到的 102 放进 `pending`，等 101 确认后再吃掉。

从序号 1 开始全量同步时，不必走这个跳跃：`floor = 0`，`confirmed_seq = 0`，然后只按推进规则向后拉。

向上翻页用 `direction = 1`，把 `floor` 往下移。翻页结果不放进 `pending`，也不把 `confirmed_seq` 往回调。

## 重连

1. 用本地 `confirmed_seq` 拉 `direction = 2`。
2. 同时可以重新建长连接。建连期间先到的推送照样进 `pending` 或推进规则。
3. 拉到返回的 `last_seq` 与 `confirmed_seq` 相等，并且 `pending` 里没有比它更大的序号，才算追上。
4. 追上之后新消息以推送为主，偶尔用同一次拉取对一下 `last_seq`。对不上就再补一轮。

长连接的 `conn.ready` 不携带消息，也不表示已经同步完成。

## 不要这样做

- 用消息 id、`ct` 或到达顺序推进游标
- 用对方的序号、或两边序号的最大值，当作自己的游标
- 收到大于 `confirmed_seq + 1` 的推送时，把中间当成没有消息
- 拉取结果第一条已经跳号时，仍把本页最大序号记成已确认
- 用列表接口上一次看到的旧 `last_seq` 判断「已经拉完」
- 把 `pending` 里的消息先画进时间线，再指望以后有机会补洞
