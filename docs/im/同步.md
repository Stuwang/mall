# 客户端同步

服务端不记每个设备同步到哪。每台设备自己留两个游标，断线、丢推送、换设备都靠拉接口补。

已读、未读不参与同步。

## 本地要记住的状态

| 状态 | 含义 |
|------|------|
| `list_cursor` | 会话列表已经按 `last_seq` 升序应用到的位置。下一轮列表请求把它放进 `after_seq` |
| 每场 `history_cursor` | 这场历史已经按序号应用到的位置。下一轮历史请求把它放进 `after_seq`。新会话从 0 开始 |
| 消息 | 按 `msg_id` 保存。同一 id 再到达时覆盖正文、序号和 `ut` |
| `sending` | 已在本地显示、还没有服务端 `msg_id` 的气泡，按 `client_msg_id` 暂存 |

`conv_id` 在发请求前就算好：整数较小的用户 id、下划线、整数较大的用户 id。发送还没成功的本地会话用这个键放着。

列表接口带回的 `last_seq` 是这场要追上的水位，不是 `history_cursor`。一场从列表里第一次出现时，`history_cursor` 仍是 0，然后再拉历史。

## 什么时候拉

- 长连接建上之后
- 收到 `msg.push` 之后
- `send` 成功之后
- 应用回到前台，以及一个较慢的定时器

推送和发送响应先到时，可以按 `msg_id` 把那一条写进本地并立刻显示。`list_cursor` 和 `history_cursor` 都不在这一步前移。随后拉 `conv/list`。若当前开着这场会话，再拉它的 `msg/history`。短时间里连续多条推送，合成一次拉取。

定时器和重连使用本地仍保存的游标，从缺口后面继续，不必从 0 再拉全量。新设备本地没有游标，列表从 0 开始，每场历史也从 0 开始，直到追上。

## 列表

`conv/list`，`after_seq` 等于 `list_cursor`。`limit = 0` 时这次能返回的都返回。

处理响应：

1. 按 `conv_id` 盖住本地已有的服务端会话。每场的 `last_seq`、最新消息、`sort_ut` 以响应为准。
2. 本地还有未成功发送的会话，响应里没有它：保留。不要用这次列表把草稿删掉。
3. `has_more = false`：若列表非空，`list_cursor` 改成其中最大的 `last_seq`。列表为空则游标不动。
4. `has_more = true`：结果已按 `last_seq` 升序。`list_cursor` 改成本批最后一条的 `last_seq`，用新游标再请求。

展示顺序用各会话的 `sort_ut` 倒序，与拉取顺序无关。

## 历史

`msg/history`，`after_seq` 等于这场的 `history_cursor`。服务端返回这一侧 `seq` 更大的消息，按 `seq` 升序，并带上此刻的 `last_seq`。

处理这一页：

1. 每条按 `msg_id` 覆盖。序号变了仍是同一条，不另插一行。
2. 本页数量达到 `limit`：`history_cursor` 改成本页最后一条的 `seq`，继续拉。这时不要改成响应里的 `last_seq`，后面还有没返回的号。
3. 本页没满：`history_cursor` 改成响应里的 `last_seq`。中间缺的号是更新作废的，或属于这个用户的其他会话。
4. 本页为空，且响应里的 `last_seq` 大于请求的 `after_seq`：过一会用原来的 `after_seq` 重试。空页不能把游标拨过还没看到的消息。
5. 本页为空，且 `last_seq` 小于等于 `after_seq`：这场已经追上。还没有成员行时，服务端返回空列表和 `last_seq = 0`。

气泡按 `ct`、`msg_id` 排。同步序号只决定拉取，不决定上下位置。

新设备把一场会话从 0 拉到 `last_seq`，本地就有全量，不另做「向上翻页」。中途若把 `history_cursor` 直接拨到最新，创建后没再改过的旧消息会留在游标下面，以后拉不到。

## 推送和发送响应

`msg.push` 和 `send` 响应里的消息，用 `msg_id`（发送响应还可以用 `client_msg_id`）对上本地那一条，写上服务端字段，立刻显示。

发送响应里的会话快照可以盖住这一场的预览，让列表马上有这一行。快照里的 `last_seq` 仍是水位。`history_cursor` 等历史接口按上面的规则前进。

先推到序号 10、序号 9 的推送丢了：10 可以先显示，`history_cursor` 还停在 9 之前。紧接着的历史请求从原游标拉，9 和 10 都会回来。若显示 10 时把游标改成 10，后面的历史、定时同步和重连都不会再带回 9。

`send` 两条并发、后发的响应先到，同样不推进 `history_cursor`。

## 多端

每台设备保存自己的 `list_cursor` 和各场 `history_cursor`。一台已经追上，另一台还停在较早的游标，互不影响。

发送者的其他在线设备会收到 `msg.push`。发起这次 HTTP 的设备用 `client_msg_id` 对上已经在屏幕上的气泡。

## 和以后删除的关系

本期没有删除。以后删除若要能同步到已经拉过这条的设备，应保留消息行，标成已删除，并给看得到的一侧一个新序号。客户端按 `msg_id` 盖掉本地。只把行从库里删掉，增量接口不会再提到它。

区间补洞（本地持有若干段序号、向服务端要差集）留到游标必须跳着走的时候再做。现在两个游标都只确认一个前缀。
