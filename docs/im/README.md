# IM 审查稿

仓库总览见 [文档](../README.md)。下面是 IM 自己的方案，供审查。这里定范围和契约。业务事务还没写。

IM 是独立服务。它和商城业务没有关系，也不读写商城的库、文件和密钥。两边只共用 `modules` 里的代码：

| 模块 | IM 用它做什么 |
|------|----------------|
| `modules/kit` | 日志、JWT、错误码、HTTP 响应、一致性哈希 |
| `modules/user` | 注册、登录、资料、封禁 |
| `modules/file` | 代码可引用。一期消息只有文本，不走上传 |

这些模块由 IM 进程自己初始化。用户表和聊天表都在 IM 的 `im.db` 里。

先看 [字段](字段.md) 和 [同步](同步.md)。同步序号是每个人自己的，两边可以不一样。列表排序用的是另一列时间。

## 这一版定下来的点

1. **不建 `im_conversation`**。一场私聊由 `conv_id` 标识，规则是较小的用户 id、下划线、较大的用户 id。成员行和消息行都写这个字符串。没有可见消息就不建成员行。
2. **同步序号按用户计数**。这个用户的所有会话共用一条递增序列。只有他看得到的新建和更新才占号。会话上的 `last_seq` 是这一场里他拿到过的最大序号。
3. **消息更新把这一侧的序号改成更大的新值**。旧号留空。客户端按 `msg_id` 覆盖本地行。气泡顺序看创建时间，不看同步序号。
4. **最新消息单独记 `last_msg_id`**。它按创建顺序选取。排序时间是这条消息的 `ut`，冗余在成员行上，列表展示用它倒序。
5. **双方各自维护** `last_seq`、`last_msg_id`、排序时间和预览。系统消息只给一侧看时，只动那一侧。
6. **列表和历史都是增量同步**。客户端保存本地数据，用自己的游标来拉。推送带完整消息，可以先显示，游标只由对应接口的响应推进。
7. **没有 open**。还没发出去的会话留在本地。服务端在第一条可见消息落库时建成员行。
8. **发送只走 HTTP**。`client_msg_id` 幂等。长连接只有心跳和 `msg.push`。
9. **用户自己发的消息双方都看见**，两侧预览都更新。系统代发仍可指定可见性和预览开关。
10. **正文只有文本**。服务端不做已读回执和未读数；客户端可按 [同步](同步.md) 在本机维护未读。撤回、删除本期都不做。
